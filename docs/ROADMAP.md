# Roadmap

Each step is sized for one Claude Code session. Tick it off when `npm run build` and `npm test` pass.

## Phase 1 — Foundation
- [x] **1.1 Scaffold**: Vite + React + TS, ESLint, Vitest, folder layout from CLAUDE.md. Import `tokens.css` + `bundle.css`, copy fonts. Show an empty `AppShell` with `Sidebar`.
- [x] **1.2 Primitives**: port Icon, Logo, Button, IconButton, Badge, Kbd, Avatar, Input, Field, Select, Checkbox, Radio, Switch, SegmentedControl to `.tsx`.
- [x] **1.3 Model**: `src/core/model.ts` from `index.d.ts`; `validate.ts` (column/table name rules) with tests.

## Phase 2 — Workspace
- [x] **2.1 Store**: Zustand schema store (tables, positions, selection, dirty flag) + undo/redo (zundo). Load the ecommerce sample.
- [x] **2.2 Canvas**: port TableNode + ERCanvas (drag, pan, zoom, edges, minimap, legend, context menu).
- [x] **2.3 Inspector**: port Inspector, TypeSelect, ColumnEditor; edits go through the store.
- [x] **2.4 Toolbar + StatusBar**: save state, undo/redo, zoom, search, shortcuts (⌘S/⌘Z/⌘K/F2/⌫/Esc).
- [x] **2.5 Dialogs**: Modal, ConfirmDialog (delete table), Toast.

## Phase 3 — Persistence & list
- [x] **3.1 Dexie**: schemas + versions tables; save creates a new immutable version snapshot.
- [x] **3.2 Schema list screen**: DataTable with search, engine filter, sort; New Schema; Empty state.
- [x] **3.2a New table**: "New table" in the canvas menu (right-click) and in the inspector; the table is selected and its name put into rename mode.
- [x] **3.2b Delete schema**: row menu and ⌫ in the schema list, confirmed in a dialog; removes the schema with all its versions.
- [x] **3.3 Routing**: list ↔ workspace ↔ history ↔ diff (react-router or simple state router).

## Phase 4 — Import / Export (MVP done here)
- [x] **4.1 Parser**: PostgreSQL `CREATE TABLE / ALTER TABLE ADD CONSTRAINT / CREATE INDEX` → model; errors with line numbers. Tests with good and broken fixtures.
- [x] **4.2 Import dialog**: DropZone, SqlEditor, live ParseStatus summary, auto-layout new tables in a grid.
- [x] **4.3 SQL generator**: model → PostgreSQL DDL with options (indexes, FKs, comments, DROP IF EXISTS). Round-trip test: parse(generate(x)) == x.
- [x] **4.4 Export dialog**: SQL / JSON, preview, download file.

## Phase 5 — Versions
- [x] **5.1 Diff engine**: compare two snapshots → DiffGroup[] (tables, columns, indexes, relationships). Tests.
- [x] **5.2 Version history screen**.
- [x] **5.3 Schema diff screen** (side-by-side DdlDiff).
- [x] **5.4 Migration generator**: diff → ALTER statements in a transaction; flag destructive changes.

## Phase 6 — Later
- [x] **MySQL dialect: parser**: `CREATE TABLE / ALTER TABLE / CREATE INDEX` as mysqldump, phpMyAdmin and hand-written DDL have them → model; Import dialog offers MySQL. Tests with dump fixtures.
- [x] **MySQL dialect: generator**: model → MySQL DDL and migrations (no transaction: MySQL commits each statement); exporting for the other engine converts the data types; the type picker offers MySQL's types in a MySQL schema. Tests, and checked against MySQL 8.
- [x] **Light/dark toggle in Settings**: a Settings dialog (sidebar, ⌘,) with the theme; kept in the browser and applied before the first paint.
- [ ] Desktop app with Tauri (open/save `.sql` files on disk)
- [x] **Infer missing relationships**: a database that declares no foreign keys gets them from the names of its columns (`orders.user_id` → `users.id`), on import and from the canvas menu. They are marked `inferred`: drawn dashed, and left out of DDL, migrations and the diff until they are made foreign keys in the column editor or included in an export. Tests with a dump that has no foreign keys.
- [x] **Connect to a live database (read-only introspection)**: the Connect to database tab of Import Schema reads the tables of a PostgreSQL or MySQL database through a local bridge (`npm run bridge`) in a read-only transaction; the catalog becomes DDL and is imported like a script. Tests with catalogs of real databases.
- [ ] **Connect through SSH**: "Connect through SSH" in the same tab reaches a database that is behind a server: the bridge logs in (password, private key file on its machine, or ssh-agent), carries the one connection of the driver through a loopback listener, and closes the tunnel when the catalog is read. The key of the server is checked: the first time the app shows its fingerprint to trust (kept in IndexedDB, `knownHosts`), and a key that changed is refused until it is trusted again. Secrets are never stored. Done, with tests against an in-process SSH server; still to do: try it against a real SSH server with PostgreSQL and MySQL, with and without SSL.
- [x] **Languages (English, Vietnamese)**: every word of the app is a message of `src/core/i18n`: `en.ts` names each one, with its placeholders and, where a number changes it, its plural forms, and `vi.ts` has the Vietnamese for all of them; a key that does not exist, or a placeholder that is left out, does not type-check. `t()` gives a message in the language of the app, in components, in the actions that show toasts and in the core (validation, the errors and warnings of the parsers, relative times, what a version changed, the summary of a diff). Language in Settings switches at once, is kept in the browser like the theme, and is the `lang` of the page. Exported SQL, JSON and migrations, with the comments in them, stay in English; a destructive change is said in the app's language in the dialog and in English in the script. Tests: both dictionaries have the same messages, placeholders and backticks, and the core answers in Vietnamese.
- [x] **Arrange tables**: "Arrange tables" in the toolbar and the canvas menu moves every table to where its relationships put it, in one undo step: each group of related tables in columns, referenced tables left of the tables that reference them (on both sides of a master table with many), the tables without a relationship in a grid beside or under them. An import is arranged the same way instead of in a plain grid. Tests with the sample and the dumps.

- [x] **7.7 Table groups**: a colour and a label for the tables of one module, suggested from the prefix of their names (`da_chung_tu*`). "Table groups…" in the canvas menu and the inspector opens a dialog that lists the groups (label, one of seven colours, remove; New group) and under them the ones the names point to: tables that begin with the same words, named after the table the others are called after, past what every table begins with (`da_`). - [x] **7.8 Lines around tables**: relationship lines are routed through the gaps instead of behind the tables between their two ends; Arrange tables leaves room for them. A line whose curve would run behind a table goes around instead: out of the side of each end, then along horizontal and vertical lines with rounded corners, the shortest way with few corners that keeps clear of every table. Lines to different columns keep different distances, so two of them in one gap do not run as one. A line that has nothing in its way stays the curve it was, and one that has no way around (a table right against its end) too. Arrange tables gives a line between tables more than a column apart a gap in each column it passes through. Tests with the sample and the dumps.
- [x] **7.9 Export the diagram**: PNG and SVG in the Export dialog. - [x] **7.10 Choose the tables of a group**: "Choose tables" on a group of the Table groups dialog lists the tables of the schema under it, each to be ticked into the group or out of it, one undo step a tick. - [x] **7.11 Resize the sidebar and the inspector**: the line between a panel and the canvas is a handle (`ResizeHandle`): dragged, it makes the sidebar 200 to 440px wide and the inspector 320 to 720px, and never leaves the canvas less than 400px of the window. - [x] **7.12 Resize tables**: a table on the canvas has a handle at either side. Dragged, it makes the table 160 to 640px wide in steps of 4px, in one undo step; the left side lands on the grid and the right side stays where it is. A double click fits the table to its text: its name and the name and type of its widest column. With several tables selected a drag of one makes them all as wide, and a double click fits each. The width is of the diagram, kept with the position: saved with a version, kept by a move, a rename and a copy, and marked as an unsaved change. Relationship lines end at the sides of the table as wide as it is, Arrange tables makes a column as wide as its widest table, and the exported PNG and SVG draw each table at its width with the text that fits it. Tests with the sample and a dump.


## Phase 8 — Sample data, versions and large diagrams
Planned and done on 2026-10-09, in this order.
- [x] **8.1 Name a version and write a note on it**: the pencil beside a version in the history opens Edit version: a name (what the list shows; blank goes back to "what it changed") and a note of up to 2000 characters, shown under the version and found by the filter. - [x] **8.3 Crow's foot and which columns a table shows**: relationship lines end in crow's foot: two bars where exactly one row is referenced, a bar and a ring where the foreign-key column may be empty, a foot and a ring for many, a bar and a ring where the column is unique. Per table, kept with the position, saved with a version, one undo step, kept by Arrange tables (which makes room for the shorter tables), in the exported PNG and SVG; lines to a column that is not shown end at the head. Tests.
- [x] **8.4 Hundreds of tables**: lines are found a pass at a time and kept while they stay right (`routeEdges`): dragging a table no longer searches for every line again, and a diagram opens at once with the lines that need a way around drawn as curves until they are found. The search itself is 4× faster. Tables and lines are memoised with stable handlers; far from the visible area they are not drawn, and zoomed out below 45% a large diagram draws table heads only. Measured in Chrome with 300 tables: opening and fitting 368 → 118 ms, panning 118 → 16 ms a frame, dragging a table 553 s → 3 s in all (8.7 s → 25 ms a frame), 26 700 → 2 900 DOM nodes. React Flow was not needed.
