# Live Data mode

Read table rows from a connected MySQL database through the local bridge, one page at a time, when Data mode opens a table.

Scope locked: **session password**, **MySQL only**, **Data mode read-only**.

## Why

Connect / Import Schema reads the catalog only (`SHOW CREATE TABLE`). Data mode then shows empty local rows in IndexedDB. A connected schema such as `atad5s` (269 tables) should show the rows that are already in MySQL, without a CSV import and without copying every table at connect time.

## What ships

- After a successful Connect import, the schema keeps a connection profile (host, port, database, user, engine, ssl, ssh without secrets).
- The password lives in memory for the browser session only. It is never written to IndexedDB or to a file.
- Opening a table in Data mode asks the bridge for one page (`LIMIT` / `OFFSET`) plus a row count for that table.
- Pagination and Refresh fetch again. The sidebar does not count every table up front.
- Add record, Import Records, Edit, and Delete are off while Live is on. Local schemas (imported from a file, with no profile) stay as they are.
- Status bar says Live data and the connection label. A missing password or a stopped bridge is an error with a way back to the connection form.

## What does not ship

- Remember password.
- PostgreSQL row reads.
- Dumping every table at connect time.
- Live writes (`INSERT` / `UPDATE` / `DELETE`).
- Query mode against the live database.
- `COUNT(*)` of all 269 tables when Data mode opens.
- Re-reading the catalog when the server DDL changes. The diagram stays the snapshot from import; the grid shows live rows.

## Flow

```text
Connect (MySQL)
  -> Import Schema (DDL, as today)
  -> save profile, keep password in session
Data mode, table T, page P
  -> POST /rows { connection, table, limit, offset, orderBy? }
  -> bridge: START TRANSACTION READ ONLY
       SELECT columns FROM `T` ORDER BY ... LIMIT ? OFFSET ?
       SELECT COUNT(*) FROM `T`
     ROLLBACK
  -> grid
```

The browser still cannot open MySQL itself. The bridge stays on `127.0.0.1` and still refuses SQL sent by the page. It builds the `SELECT` from a table name, a column list taken from the schema, and a limit.

## Steps

### 1. Connection profile

Dexie version 7 adds `connections`, one row per schema:

- `schemaId` (unique)
- `engine` (`MySQL` only for this feature)
- `host`, `port`, `database`, `user`
- `ssl?`, `ssh?` (host, port, user, auth, key path — no password, no passphrase)

`src/store/session.ts` (or a field on the UI store) holds `{ schemaId, password }` in memory. Reload clears it.

After Import Schema from Connect succeeds, save the profile and the session password. File import does not.

### 2. Bridge `POST /rows`

`bridge/server.ts` gains `/rows`, next to `/introspect`. Body is the same connection object plus:

```ts
{
  table: string;
  columns: string[];          // from the imported schema, so the SELECT lists known names
  limit: number;              // 1..200
  offset: number;             // >= 0
  orderBy?: { column: string; dir: 'asc' | 'desc' };
}
```

Rules:

- Engine must be `MySQL`. Anything else is 400.
- `table` and each column match `^[A-Za-z0-9_]+$` and are quoted with backticks. Reject anything else.
- `orderBy.column` must be one of `columns`.
- Run inside `START TRANSACTION READ ONLY`, then `ROLLBACK`, same as the catalog read.
- SSH tunnel is reused from `readCatalog`.
- Answer: `{ ok: true, rows, total }` or the same error shape as `/introspect` (`connect` / `read` / `ssh` / `hostKey`).

`src/bridge/client.ts` gets `readRows(...)`, which never throws: a stopped bridge comes back as `bridge.notRunning`.

Raise the body limit only as far as a connection plus a column list needs. It stays well under a megabyte. Rows travel back, not in.

### 3. Data mode

`useRecords` takes a live branch:

- Profile present and session password present: call `readRows` for the open table and the current page. `counts` has a number only for that table.
- Otherwise, if a profile exists but the password is gone: fail with a prompt to enter it again (the Connect form, password only).
- No profile: today's IndexedDB path.

`DataMode` maps the page size and page number to `limit` / `offset` and refetches. Refresh refetches. Sort of one column, when it is on, is `orderBy`. Search and the filter popover stay client-side on the current page for this version (they do not pretend to search the whole table).

While live:

- Disable Add record, Import Records, row edit, duplicate, and delete.
- Status bar uses `data.liveData` and the connection label.
- Empty grid means the table has no rows, not that the import failed.

### 4. Words

Add messages to `src/core/i18n/en.ts` and `vi.ts`: live badge, read-only hint, password needed, row read failed. Exported files stay English; these strings are UI only.

### 5. Checks

- Vitest for the request parser: bad table name, bad engine, limit cap, missing password field on the connection.
- Vitest for `readMysqlRows` against a small in-memory or fixture MySQL is optional if the suite has no server; the SQL string and the identifier check are the required tests.
- `npm run build` and `npm test`.
- By hand, with `npm run bridge` and `atad5s`: open `da_nhan_vien`, page through, Refresh, reload the app and confirm the password is asked again and the rows come back.

## Order

1. Types + Dexie 7 + session password store, with a test that the password is not in the stored record.
2. Bridge `/rows` for MySQL + client `readRows` + parser tests.
3. `useRecords` live branch and Data mode read-only UI.
4. Save the profile when Connect import succeeds.
5. Try `atad5s`.

## Risks

- `COUNT(*)` on a large table is slow. Accept it for the open table only; do not fan out.
- The diagram can drift from the server. The grid uses the column list from the imported schema. A column added on the server after import is invisible until the schema is imported again.
- A page-local search will miss rows on other pages. Say so in the search placeholder only if it is cheap; otherwise leave it and note it here.
